# Handoff: fix an error in a finished MusicXML, then remake its stems, mp3s and videos

Written 2026-09-27 for a fresh session. Read this file, then SKILL.md Steps 4-6 (element order,
verify, Cantai mode), 9.1-9.4 (stems, audit, mix) and 10 (videos). Everything named below is in
this repository or in the song's own folder; nothing needs to be fetched.

## Suggested first message for the new session

> Read `~/Cowork/rehearsal-tracks/handoff-score-fix.md`. The error is in [song folder], bar [n],
> [part]: [what is wrong and what it should be]. Fix it and tell me which staves to re-export.

## 1. Find out exactly what is wrong, and where it lives

- Get from the user: the song, the bar (as printed), the part, what is there now and what
  should be. If they are working from the PDF, look at that bar in the PDF yourself before
  editing (render the page and read it; SKILL.md 2.2-2.4 on reading pitch, rhythm and lyrics).
- A song folder usually holds several MusicXML files that carry the same notes: the
  print-faithful file, an open score (one part per voice), the Cantai learning copy (the one
  the stems were rendered from), and sometimes a closed display file for the videos. List
  every one, and for each say whether the error is in it. The fix goes into every copy that
  has the error, or the files disagree from then on.
- **Check for a build pipeline first.** If the song folder has a `_build/` directory or a
  `HANDOFF.md`, the files were generated by scripts: fix the script or its data, rebuild, and
  confirm the rebuild changes only what you meant (below). A hand edit to a generated file is
  lost on the next rebuild. Read that `HANDOFF.md` for the rebuild steps and the current
  checksums, and update both when you are done.
- The Cantai copy is made from the open score by `cantai_mode.py` (SKILL.md 6), with
  `--parts` and `--untie-all` as recorded in the folder's notes or the `_build/finalize.py`
  that made it. Prefer fixing the open score and regenerating the Cantai copy over editing
  both by hand; then diff the new Cantai copy against the old one to see that only the
  intended bars changed.

## 2. Edit and verify

- Keep MusicXML element order (SKILL.md 4): Sibelius rejects what other readers accept.
- Save the corrected files under the same names only after the user agrees; until then write
  them beside the originals with a suffix, so nothing is lost. The session cannot delete in
  connected folders: when old copies need removing, give the user `rm` lines in the same
  Terminal block as any git commands.
- Diff old against new, note by note (pitch, duration, tie, lyric, per part and bar), and
  show the user the list. It should hold the fix and nothing else.
- Run `verify.py` on the print-faithful file with its PDF (SKILL.md 5) and report the table as
  printed. Compare with the last recorded verify result for that file if the folder has one:
  a check that newly fails is yours.

## 3. Stems (the user re-exports; you check)

- Only the staves whose notes, rhythm or words changed need re-exporting. A Cantai render is
  never the same twice (SKILL.md 9.1), so do not ask for untouched staves.
- Give the user the recipe in plain words: import the corrected Cantai MusicXML into Sibelius
  (or make the same change in the `.sib`), open the Mixer (Play > Mixer, or M), and wait until
  every Cantai voice's panel has stopped showing the spinning halo and the pulsing dot beside
  "Rendering...". Then File > Export > Audio, one staff at a time, soloed; not the batch
  plug-in. Ask them to name the new files so they cannot be mistaken for the old ones.
- Run `stem_audit.py` on the whole set (new stems plus the untouched ones, accompaniment
  included) against the corrected Cantai MusicXML, and confirm every flag by hand as
  `handoff-stem-audit.md` step 4 describes. Save the audit text in the song folder.
- **Level.** A re-exported staff can come out at a different level from the one it replaces:
  one re-export came out 3.68 dB louder throughout, and the mix took it with
  `--trim "Bass=-3.68"`. Measure the new stem against the old one in the bars that did not
  change and trim by the difference, so the balance stays what the user already approved.

## 4. Mixes

- Remake the song's full mp3 set with `rehearsal_mix.py` (SKILL.md 9.4): voices lowest first,
  the accompaniment with `--accomp`, and the same `--trim`, `--place` and `--section` values as
  the set being replaced. SKILL.md 9.4 records the trims and placements used so far, by piece
  description; the level report the script prints should suggest the same trims.
- The Chorus Connection names are already settled: take them from the mp3 file names now in
  the folder (the user renamed some by hand; a division is `(Tenor 2) a`, never
  `(Tenor 2a)`). Make only the tracks the folder already has (some sets have no "Balanced
  panned" track).
- Confirm the new Balanced mp3 is built from the stems you meant: a least-squares fit of the
  mp3 on the stems leaves a residual 35-45 dB down when it is.

## 5. Videos

- Remake the follow-along videos with `score_video.py` (SKILL.md 10), using the song's
  `* - video checks.txt` as the record of the last run: the score, the `--display` file, the
  mp3s, and the `--anchor` values set by hand.
- Anchors before the corrected bar still apply. After it, they apply only if the fix left the
  timing alone; a changed duration, fermata, caesura or tempo moves every later bar, so
  re-measure those anchors (SKILL.md 10 on caesuras, fermatas and consonant-led attacks).
- Target the lights 25-30 ms ahead of the sound, measured per section on attacks, not
  averaged over 15 s windows. Replace the video checks file with the new run's.
- One piece also has a concert-footage video (a concert recording time-adjusted to the
  Balanced audio and stacked above the Balanced video). Its script and timing data are in that
  song's `_build/` folder, with instructions at the top of the script. Remake it whenever that
  song's Balanced mp4 changes. If the fix changed the timing, its timing data is stale: redo
  the line-up as the script's header says.

## 6. Delivery

- Stage every delivery into a new directory; a re-used staging path once wrote old copies.
- Check what landed on the user's computer: compare audio streams
  (`ffmpeg -i x -map 0:a -c copy -f md5 -`), not file sizes; files arrive a few KB larger with
  the audio intact.
- Long renders: the linked computer's shell stops each call at 3 minutes and kills background
  jobs when the call returns. Split renders into chunks that each finish in time, or run them
  in the cloud workspace; files over 20 MB cannot be copied from the cloud workspace to the
  computer, so large videos are best rendered on the computer in chunks.
- Update the song folder's notes: the stem audit, the video checks, and `HANDOFF.md` if there
  is one (new checksums, what changed and why).

## The user's working conventions

- The user runs all commits and pushes. Give one Terminal block with the git commands, and any
  `rm` lines in the same block. Use `git --no-optional-locks` for read-only git on the user's
  computer.
- No song titles, composers or lyrics in repository files or commit messages; the song's own
  folder is where names belong.
- Write tempo in plain text ("half = 138"), not note glyphs.
- Style: no LinkedIn cadences, no softened criticism, no closing summary paragraphs. Verify
  any citation by fetching it and quote a sentence from it.
